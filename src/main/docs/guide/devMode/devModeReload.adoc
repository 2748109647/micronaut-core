A change is handled as one batch: files saved together, across several directories, are compiled and applied together.

Sources:: The changed files and, through an index of which classes reference which, every source whose classes link against a changed or deleted class are compiled with the compile classpath, the annotation processors and the options the build uses. The class files and generated sources go to a staging directory and replace the output only when the compilation succeeded, so a broken edit leaves the running application as it is; the errors are logged and, when an HTTP server runs, shown to a browser in place of the page, until the next successful compilation.
Classes:: When a class file changed, the application restarts on a new generation: the context of the previous generation is stopped, retaining what a api:context.reload.BeanRetentionPolicy[] asks for, a new generation of the class loader is created over a fresh snapshot of the output, and the application's `main` runs again. The retained singletons are adopted by the new context under their definitions, so a bean that depends on them is created on top of the same instance. api:context.reload.ClassChangeEvent[] is published to the old context before it stops, and api:context.reload.ReloadCompletedEvent[] to the new one once it started.
Method bodies:: With `micronaut.dev.strategy=auto` (the default) or `reload`, an edit that changes only method bodies, the structure of every changed class being the same and no generated class having changed, is applied in place: the JVM redefines the loaded classes through the agent and the running beans see the new bodies, in tens of milliseconds and without a restart. The agent is `micronaut-dev` itself, launched with `-javaagent`, which the build plugins add; without it, or with `strategy=restart`, every change restarts.
Python modules:: A Python edit that changes only bodies leaves the classes the compiler generates byte for byte the same: only the module and the bytecode written for it change in the class output. Such a change, in which no class changed and no file was added or removed, is offered to the running context's api:context.reload.InPlaceResourceReloader[] beans before anything restarts. The Python runtime's reloader patches the edited modules into every GraalPy context of the application, the primary one, the pooled ones and those of the asyncio event loops: the module, class and function objects stay, the functions run the new code, the classes get the new members, and the module's other globals are rebound, except the ones the application injects. The generation keeps running, under every strategy, `restart` included, since nothing is redefined; `micronaut.dev.patch-in-place=false` turns it off. What the merge cannot follow is refused and restarts instead: a changed base class or metaclass, a function that became a class or a generator, a closure over other variables, a package initialiser (`__init__.py`) or the main script, and a module the compiler generated. Patching is not atomic across contexts: a failure in any of them restarts the application, whose new generation discards what the others applied. Module-level code runs again when a module is patched, so a side effect of it, a registry filled at import, happens again.
Resources:: A changed template, static file or message bundle does not restart anything: it reaches the beans that watch resources of that kind (see the next section). A changed configuration file restarts the application, retaining nothing.

Retaining a bean:: The manifest's `micronaut.dev.retain` names the types to keep across restarts; a module can contribute a api:context.reload.BeanRetentionPolicy[] bean instead, which is consulted for every singleton when the context stops and retains it, refuses it or abstains. A bean is retained when a policy retains it and none refuses it, whatever their order, so a module can refuse what `@Retain` or `micronaut.dev.retain` asks for, such as a client whose configuration names a class of the application that the client instantiates and keeps; a bean that holds a refused bean is not retained either, and the refusal is logged at debug under `io.micronaut.context.lifecycle`, naming the policy. A bean is only retained when its class and everything it received, as the dependency graph records, come from the runtime classpath rather than the reloadable tier: a bean that holds an application class cannot survive a change to that class. A module declares which of its beans are retained with api:context.annotation.Retain[], on the bean's class or on the factory method that produces it, as a module that defines a connection pool does so that a restart keeps the pool, and an in-memory database with it; the bean is dropped and created again when the configuration it was made from changes. That configuration is found from the dependency graph: the prefix of every configuration bean in the retained bean's closure, a `@ConfigurationProperties`, an `@EachProperty` entry or another configuration reader that the bean, the factory that produced it or any singleton it holds received, nested configuration included, releases it without being named, and an `@EachProperty` entry counts under its own prefix, so a change of one entry releases only the beans made from it. `invalidatedBy` then only names what the bean reads outside configuration beans, such as a raw `@Property` or `@Value`; with an empty `invalidatedBy` the bean is released by the configuration of its closure alone, and the prefixes a policy's `observedConfigurationPrefixes` declares add to it in the same way. A configuration bean in the closure does not keep the bean from being retained and is not retained with it: each generation binds it again, so the retained bean must copy the values it needs rather than keep the configuration bean. Set `micronaut.dev.retain-annotated=false` to retain only what `micronaut.dev.retain` names. A pool that a `BeanCreatedEventListener` wraps, as Micronaut Data wraps a data source, is retained as the listener received it and wrapped again by the new context's listeners. A pool is not retained when the factory that made it holds the application context, since destroying the factory would close it: the log says why.

The console shows what each reload did, the generation started, the time it took, the classes changed and the beans retained. Once the new generation serves, the runtime checks that generations older than two are no longer reachable and warns when one is: a static cache in application code or a thread that was never stopped is the usual cause.
